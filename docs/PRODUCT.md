# 1. 产品定义

**O3Pilot** 是面向 Ozon Global 跨境卖家的业务数据、经营分析与决策支持系统。

O3Pilot 将 Ozon 可读取业务数据、Ozon Push Webhook、用户主动导入的 Ozon 官方报告以及卖家自有经营数据统一到一致的数据体系中，并在此基础上提供业务监控、经营分析、异常识别、利润分析和决策支持。

O3Pilot 的核心目标不是复制 Ozon Seller Center，也不是建设 ERP，而是回答四个问题：

1. 当前发生了什么？
2. 为什么发生？
3. 是否存在异常或风险？
4. 接下来应该关注或采取什么经营动作？

O3Pilot 提供数据、分析和建议。

**O3Pilot 不主动修改 Ozon。**

# 3. 产品边界

## 3.1 O3Pilot 可以

O3Pilot 可以：

- 读取 Ozon Seller API；
- 读取 Ozon Performance API；
- 接收 Ozon Push Webhook；
- 查询 Ozon 当前业务状态和只读配置；
- 保存 Ozon 原始数据；
- 建立历史数据；
- 标准化和关联业务对象；
- 导入用户主动提供的 Ozon 官方报告；
- 导入卖家自有经营数据；
- 计算业务指标；
- 发现异常；
- 分析利润；
- 进行历史回测；
- 建立预测模型；
- 提供经营建议；
- 发送 O3Pilot 自身的提醒和通知。

---

## 3.2 O3Pilot 永远不主动修改 Ozon

禁止：

- 创建、修改、删除商品；
- 修改商品属性；
- 修改商品内容；
- 修改价格；
- 修改库存；
- 创建或取消订单；
- 修改订单状态；
- 执行备货或发货；
- 修改仓库；
- 修改物流配置；
- 创建或修改广告；
- 修改广告商品；
- 修改广告预算；
- 修改广告出价；
- 创建、修改、启用或删除 Webhook 订阅；
- 回复或发送 Ozon 聊天消息；
- 自动回复评价；
- 修改促销配置；
- 修改其他 Ozon 服务端业务状态。

即使 API Key 拥有相关权限，也不得突破这一边界。

**API 能做什么，与 O3Pilot 被允许做什么，是两个不同概念。**

# 5. 能力分类

O3Pilot 的所有产品能力使用统一分类。

| 类型 | 含义 |
|---|---|
| **A — 自动读取** | 可以通过 Seller API、Performance API、Webhook 等自动获得 |
| **B — 派生计算** | 原始数据不直接提供结果，但已有足够数据可以计算 |
| **C — 卖家数据** | 需要结合卖家自己提供的数据 |
| **D — 官方报告** | 需要人工导入 Ozon 官方报告才能获得或核验 |
| **X — 当前不可可靠实现** | 当前没有可靠数据来源或尚未验证 |
| **禁止** | 技术上可能支持，但违反 O3Pilot Read-Only 产品边界 |

一项能力可以同时属于多个类型。

例如：

**真实 SKU 利润 = A + B + C**

因为它同时需要 Ozon 财务事实、O3Pilot 计算和卖家采购成本。

# 6. 多店铺

O3Pilot 从第一版开始按照多店铺系统设计。

不得假设：

- 永远只有一个店铺；
- 永远只有两个店铺；
- 所有店铺使用相同结算货币；
- 所有店铺拥有相同 API 权限；
- 所有店铺拥有相同商品；
- 所有店铺使用相同履约方式；
- 所有店铺拥有相同数据覆盖。

所有核心数据都必须能够追溯到所属店铺。

# 9. 数据新鲜度

不同数据源拥有不同实时性。

O3Pilot 必须明确显示：

- Webhook 事件时间；
- API 最后同步时间；
- 数据实际覆盖时间；
- Ozon 官方报告导入时间；
- 卖家自有数据更新时间。

不能因为不同数据出现在同一页面，就表现为拥有相同实时性。

---

# 10. 货币

O3Pilot 必须区分：

- API 原始币种；
- Marketplace 展示货币；
- 店铺结算货币；
- O3Pilot 分析货币；
- 汇率；
- 汇率日期。

原始金额必须尽可能保存：

- 金额；
- 币种。

转换后的金额必须能够追溯：

- 来源币种；
- 目标币种；
- 汇率；
- 汇率日期；
- 转换规则。

不得假设：

**店铺结算货币 = 所有 Ozon API 金额币种。**

---

# 11. 时间

原始业务时间必须保留。

O3Pilot 默认业务展示和统计时区：

**Asia/Shanghai（UTC+8）**

展示时间转换不得覆盖原始时间。

---

# 12. 当前不可靠或未验证能力

某项能力只有在存在经过验证的数据来源时，才能正式进入 Capability Map。

不能因为 Seller Center 页面存在某项功能，就默认 API 可以获得完整数据。

例如以下类型能力必须保持谨慎：

- 完整竞争对手商品数据库；
- 任意竞争对手历史销量；
- 任意竞争对手真实库存；
- 无数据基础的市场预测；
- 无可靠对应关系的 SKU 财务分摊；
- 无法取得原始数据的 Seller Center 专属指标。

如果未来 Ozon 提供可靠数据源，再更新对应 Capability。

# 13. 产品能力与开发阶段分离

**Capability 是否存在**与**什么时候开发**是两个不同问题。

PRODUCT.md 首先记录当前所有合理可实现能力。

开发阶段只决定优先级。

不能因为某项能力不是 Phase 1，就认为它不存在于 O3Pilot 产品范围中。

# 16. 成功标准

O3Pilot 应逐步达到：

1. 当前重要 Ozon 业务数据都有明确归属；
2. 当前能够实现的产品能力已经在 Capability Map 中登记；
3. 新功能首先映射到现有 Capability，而不是随意创建新业务模块；
4. 多店铺数据严格隔离；
5. 原始数据可以追溯；
6. 订单、商品、库存、物流、退货和财务可以关联；
7. 未知不被伪装成 0；
8. 派生数据与原始事实明确区分；
9. 数据新鲜度清晰可见；
10. 产品退货率、取消率和未认购率具有独立口径；
11. 财务费用能够说明数据来源；
12. 利润能够说明组成部分；
13. 费用分摊可以解释；
14. 预测可以回测；
15. 所有 Ozon 操作保持严格只读；
16. API Key 即使拥有写权限，O3Pilot 也不会执行 Ozon 写操作。

# 18. 核心原则

**先确定业务事实。**

**再确定数据是否可以获得。**

**再确定能力是否可以实现。**

**再决定什么时候开发。**

**先保证数据正确，再计算指标。**

**先保证指标可信，再建立分析。**

**先保证分析可解释，再给出建议。**

**只提供建议，不主动修改 Ozon。**
